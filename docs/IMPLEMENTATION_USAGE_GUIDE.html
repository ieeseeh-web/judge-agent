tool_argument_mismatch Detector

F-101 ✅ 완료
Tool 호출 인자가 사용자 요청과 불일치하는 경우 감지
📌 감지 조건
HIGH

Status 범위 불일치

사용자가 5xx 분석을 요청했는데 filter_log_records의 status_min/max가 5xx 범위(500~599)를 포함하지 않는 경우.

MEDIUM

Path 필터 누락

사용자 요청에 target endpoint가 명시되어 있는데 filter_log_records의 path_pattern이 None으로 호출된 경우.

🧪 재현 방법 (테스트)
bash
# drift-wrong-endpoint fixture로 재현
python3 -m judgeagent.reference.agent.weblog_agent.cli \
  run-fixture drift-wrong-endpoint --no-llm

# Judge Agent로 분석
python3 -m judgeagent.backend.cli analyze \
  --trace artifacts/weblog-reference/drift-wrong-endpoint.jsonl
Finding 확인: 분석 결과에서 metric: "tool_argument_mismatch", severity: "high" 항목을 확인합니다.
📄 Finding 예시
JD-011 HIGH tool_argument_mismatch tool
Expectedfilter_log_records status range should cover 500~599 for 5xx analysis. ActualActual range [400, 499] does not cover 5xx status codes. Evidenceuser_input contains '5xx' request · filter_log_records called with status_min=400, status_max=499

repeated_tool_call Detector

F-102 ✅ 완료
동일 Tool 반복 호출 / ReAct 루프 감지
📌 감지 조건
HIGH/MEDIUM

단순 반복 호출

동일 tool이 임계값(repeated_tool_call_threshold: 5) 이상 호출된 경우. 5~9회: MEDIUM, 10회+: HIGH.

HIGH

완전 동일 패턴 반복

동일한 thought + action 조합이 3회 이상 반복되어 에이전트가 진행하지 못하고 루프에 빠진 경우.

임계값 조정: judgeagent/judge_agent/config/detector_rules.json의 repeated_tool_call_threshold 값을 수정하면 임계값을 변경할 수 있습니다. (기본값: 5)
⚙️ 설정 변경
json
// detector_rules.json
{
  "reference_weblog": {
    "repeated_tool_call_threshold": 5,   // 기본값: 5회 이상이면 finding 생성
    ...
  }
}

context_hallucination Detector

F-103 ✅ 완료
Final output 수치가 Tool 실제 산출값과 불일치할 때 감지
📌 동작 원리
  1. 1
    Tool 출력 수집

    compute_log_metrics tool_end 이벤트에서 error_rate, request_count, error_count 등 수치를 수집합니다.

  2. 2
    Final output 수치 추출

    최종 보고서에서 정규식으로 동일 지표 수치를 추출합니다 (퍼센트/소수 두 형태 모두 처리).

  3. 3
    오차 비교

    허용 오차(metric_hallucination_tolerance: 0.1)를 초과하는 차이가 있으면 critical finding을 생성합니다.

예시: Tool이 error_rate: 0.15(15%)를 반환했는데 Final output에 error_rate: 99.99%가 적혀 있으면 CRITICAL finding 발생.
🧪 재현 방법
bash
# drift-metric-hallucination fixture로 재현
python3 -m judgeagent.reference.agent.weblog_agent.cli \
  run-fixture drift-metric-hallucination --no-llm

python3 -m judgeagent.backend.cli analyze \
  --trace artifacts/weblog-reference/drift-metric-hallucination.jsonl \
  --json /tmp/result.json

# context_hallucination finding 확인
python3 -c "import json; r=json.load(open('/tmp/result.json')); [print(f['metric'], f['severity']) for f in r['findings']]"

Run 히스토리 조회 UI

F-201/202 ✅ 완료
과거 Reference Run을 필터링하고 Judge/Baseline에 재사용
🖥️ 화면 접근 방법
  1. 1
    좌측 Reference Agent 패널 상단 탭 확인

    패널 상단에 Chat | Run History 탭이 표시됩니다.

  2. 2
    Run History 탭 클릭

    저장된 모든 Reference Run 목록이 최신순으로 표시됩니다.

  3. 3
    필터 적용

    상단 필터 바에서 상태(Succeeded/Failed), Fixture ID, 모델 ID로 목록을 좁힐 수 있습니다.

  4. 4
    액션 버튼 사용

    각 run 행 오른쪽의 🔬 버튼으로 Judge, 🚩 버튼으로 Set Baseline을 직접 실행합니다.

Judge 버튼 클릭 시: 해당 run이 현재 run으로 설정되고 Chat 탭으로 전환됩니다. 헤더의 "Judge this trace" 버튼을 클릭해 분석을 시작하세요.
🔌 API 필터 파라미터
http
GET /api/reference/runs
  ?fixture=normal-login-error-spike   # fixture ID 필터
  &modelId=gemma4:latest              # 모델 필터
  &status=succeeded                  # 상태 필터 (succeeded | failed)
  &from=1748000000                   # Unix timestamp (from)
  &to=1748100000                     # Unix timestamp (to)
  &limit=50                          # 최대 반환 수 (기본: 50)
bash
# 예시: succeeded 상태의 gemma4:latest 실행 목록
curl "http://localhost:19001/api/reference/runs?status=succeeded&modelId=gemma4:latest" \
  | python3 -m json.tool | head -50

SQLite 기반 저장소

F-301 ✅ 완료
기존 파일 기반 registry.json을 SQLite로 전환 — 환경변수 1개로 즉시 전환
⚡ 즉시 활성화
USE_SQLITE_STORE = 1 SQLite 모드 활성화 (기본: 파일 기반)
bash
# .env 파일에 추가 또는 시작 시 환경변수 지정
USE_SQLITE_STORE=1 bash start.sh

# 또는 .env 파일
echo "USE_SQLITE_STORE=1" >> .env
SQLite DB 파일 위치: artifacts/frontend-api/judge_agent.db
WAL 모드로 동작하므로 동시 쓰기 충돌이 발생하지 않습니다.
📦 기존 데이터 마이그레이션

기존 artifacts/의 registry.json 파일들을 SQLite로 일괄 임포트합니다.

bash
# 1. 마이그레이션 실행 (기존 파일 그대로 유지됨)
python3 -m judgeagent.backend.api_store_sqlite migrate

# 출력 예시:
#   reference_runs: 23개 임포트 완료
#   analyses: 8개 임포트 완료
#   judge_sessions: 5개 임포트 완료
#   마이그레이션 완료: 총 36개 레코드 → artifacts/frontend-api/judge_agent.db

# 2. SQLite 모드로 재시작
USE_SQLITE_STORE=1 bash start.sh
마이그레이션은 기존 파일을 삭제하지 않습니다. SQLite 모드로 전환 후 정상 동작이 확인되면 기존 registry.json을 수동으로 정리하세요.
📊 파일 기반 vs SQLite 비교
항목파일 기반 (기본)SQLite (USE_SQLITE_STORE=1)
동시 쓰기 안전성❌ uuid로 임시 완화✅ WAL 모드, 트랜잭션
쿼리/필터 성능메모리 풀 로드 후 필터SQL WHERE 절로 효율적
저장 위치artifacts/*/registry.jsonartifacts/frontend-api/judge_agent.db
백업파일 복사파일 복사 (단일 .db 파일)
추가 설치없음없음 (Python 표준 sqlite3)

GitHub Actions CI/CD 통합

F-303/305 ✅ 완료
PR 머지 전 Prompt Regression 자동 실행 및 PR 코멘트 게시
📁 워크플로 파일

파일 위치: .github/workflows/judge-regression.yml

단계동작
Step 1코드 체크아웃 (이전 커밋 포함)
Step 2~3Python 설치 + pip install -e '.[api]'
Step 4이전 커밋 기준으로 Baseline trace 생성
Step 5현재 PR 코드 기준으로 Candidate trace 생성
Step 6compare-prompt-regression 실행 → report.md + result.json 생성
Step 7GitHub Step Summary에 결과 요약 출력
Step 8PR 코멘트에 Gate / Score / Model 변경 / Findings 게시
Step 9artifact 저장 (14일 보관)
🚀 설정 방법
  1. 1
    워크플로 활성화 확인

    GitHub 저장소 → Actions 탭에서 "Judge Agent — Prompt Regression" 워크플로가 표시되는지 확인합니다.

  2. 2
    Secrets 설정 (LLM 사용 시)

    Repository Settings → Secrets → OPENAI_API_KEY를 등록합니다. Deterministic 모드는 API Key 불필요.

  3. 3
    Variables 설정 (선택)

    Repository Settings → Variables → JUDGE_LLM_PROVIDER, JUDGE_LLM_MODEL 설정. 미설정 시 none(deterministic) 모드.

  4. 4
    PR 생성 시 자동 실행

    main / master 브랜치 대상 PR이 생성되면 자동으로 실행됩니다. 프롬프트·에이전트 코드·Judge 설정 파일 변경 시에만 트리거됩니다.

🖐️ 수동 실행
bash
# GitHub CLI로 수동 실행
gh workflow run judge-regression.yml \
  -f fixture=normal-login-error-spike \
  -f fail_on_regression=true

# 실행 결과 확인
gh run list --workflow=judge-regression.yml

또는 GitHub 웹 → Actions → Judge Agent — Prompt Regression → Run workflow

⚠️ Regression 발생 시

다음 조건 중 하나라도 해당하면 CI가 실패 처리됩니다 (fail_on_regression=true일 때):

  • candidate gate가 baseline gate보다 악화됨 (gateRegressed: true)
  • Regression Score < 85
  • 새로운 high/critical finding 발생
CI 실패 시 PR 코멘트에 원인 finding이 상세 표시됩니다. Finding을 검토하고 프롬프트 또는 에이전트 코드를 수정한 뒤 재실행하세요.
